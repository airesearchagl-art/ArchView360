# ArchView360 次フェーズ設計調査（docs-only）

> 読み手: 次に実装へ着手するLLM IDE / Coding Agent、レビュー担当者
> 位置づけ: 設計調査のみ。本ドキュメントの追加自体は実装を一切含まない（`viewer.html`/`index.html`/`script.js`/`style.css`/`tests/`/package files/workflowsはいずれも無変更）。

## 背景

Viewer/Editor分離 Phase 4（`viewer.html`導入、PR #39〜#41）と、それに続くViewer詳細回帰テスト（PR-C、PR #42、`tests/e2e/viewer-html-regression.spec.js` 24テスト）が完了し、Playwrightフルスイートは147件（既存123＋新規24）を基準としている。Vaultへの記録（obsidian-vault PR #146・#169）も完了しており、未完了の既存作業はない。

本ドキュメントは、次にどのテーマへ着手すべきかを判断するための設計調査であり、実装は含まない。

## 調査方法

- 現行`docs/`配下の既存調査文書・実装ログ（Development_Log相当の情報はVault側にあるため、ここではリポジトリ内の`docs/`とREADME.mdのバージョン履歴、`tests/e2e/`の既存カバレッジから状況を確認した）。
- README.mdのバージョン履歴（v2.10〜v2.22.0）から、Undo/Redo基盤（PR #20〜#25）、Dirty State基盤（PR #14）、Viewer/Editor分離（PR #12〜#41）、VR関連機能の実装状況を確認した。
- `tests/e2e/`の既存specファイル一覧から、各機能領域のテストカバレッジの有無を確認した。

## 前提（変更しない既存方針）

- Viewer URLと Viewer Preview は責務が異なる別概念であり、混同しない。Viewer URL（`viewer.html`への直接アクセス）はセキュリティ境界ではなく、認証・権限確認の根拠として扱わない（PR #29〜PR #41時点の既存方針を踏襲）。
- `script.js`/`style.css`は`index.html`/`viewer.html`間で共有する方針を維持する。
- 本調査で提示する候補はいずれも将来の実装候補であり、本PRではdocsの追加のみを行う。

## 次の実装テーマ候補（3〜5案）

### 案A: Undo/Redoの対象拡張

PR #20〜#25で導入した`HistoryManager`基盤は、現時点でシーン名称変更・単一/比較モードのシーン左右反転・FloorMap名称変更の4操作にのみ接続されている。以下が未接続のまま残っている。

- シーン追加・削除・並び替え
- マーカー操作（配置・移動・回転・削除・番号変更）
- FloorMap画像・配置操作
- 比較セット名称・構成変更

### 案B: 空間リンク設計とVR Scene Ring再有効化

現在`VR_SCENE_RING_ENABLED = false`で無効化されているVR Scene Ring Navigationを、各sceneの実際の方向とリンク先を一致させる空間リンク設計と組み合わせて再設計・再有効化する。Roadmapの「将来構想」に記載されている「各scene間の実際の方向とリンク先を一致させる空間リンク設計」「視界内hotspot / Spatial POIによるナビゲーション」に対応する。

### 案C: リリース管理・バージョンタグ整備

現状バージョン管理はREADME.md記載のみに依存しており、GitHub Releases・タグが一切存在しない。`viewer.html`という配布用の静的エントリーポイントが確立した今、社内展開・施主共有時にどのバージョンを配布しているかを追跡する基盤を整備する。

### 案D: Quest-PC間のリアルタイム同期（Observer Mode拡張）

現状のVR Observer Modeはローカルデモのみで、Quest-PC間のリアルタイム同期（WebSocket/WebRTC）は未実装。施主説明会等で「PC画面を見ながら営業がVR内の様子を確認する」等の運用を想定する場合に必要になる。

### 案E: mp4パノラマ動画対応

現状は静止画パノラマ（JPEG/PNG/WebP）のみに対応しており、mp4パノラマ動画は未対応。D5 Render等のツールから動画書き出しへのニーズが生じた場合の拡張候補。

## 推奨案

**案A: Undo/Redoの対象拡張** を推奨する。

### 選定理由

1. **既存基盤の直接延長**: `HistoryManager`（Command Pattern、`applyXxx(id, value)`パターン、`historyManager.push()`をユーザー操作の確定地点でのみ呼ぶ設計）は既に4操作で実運用されており、新規設計を必要としない。
2. **確立された段階導入パターンが使える**: Phase 3（PR #31〜#38、G1〜G6の機能単位分割＋fail-first-then-fix＋Playwrightフルスイート2連続実行）と同じ運用パターンをそのまま踏襲できる。1回のPRで全対象を実装する必要がなく、リスクを機能単位に閉じ込められる。
3. **Editor専用機能でありViewer/`viewer.html`への影響がない**: Undo/RedoボタンとショートカットはCSSベースの確定Editor専用49件の一部として、既に`viewer.html`から完全に除去済み（PR #41）。今回の拡張が`viewer.html`側の回帰（`tests/e2e/viewer-html-regression.spec.js`）に影響を与える可能性は原理的に低い。
4. **テスト容易性が最も高い**: 既存のUndo/Redo系spec（`scene-rename-history.spec.js`等）と`window.__historyManagerForTests`という確立されたtest hookパターンをそのまま再利用でき、Playwrightのみで検証が完結する（VR実機検証やネットワーク実機検証を必要としない）。
5. **ユーザー価値が具体的**: 「一部の操作だけUndo/Redoが効く」という現状の一貫性のなさは、Editor利用者（施主説明前の編集作業を行う社内担当者）にとって分かりやすい弱点であり、対象拡張はUXの一貫性を直接改善する。

他の案（B・D）はVR実機検証や新規データモデル・通信層を伴い規模とリスクが大きく、次フェーズの最初の一歩としては重い。案Cは価値が開発運用側に閉じており緊急性が低い。案Eは需要の実在が未確認である。

## リスク（推奨案Aについて）

- FloorMap画像・配置操作、マーカー操作は、シーン追加・削除等と比べて状態が多段階（複数マーカーの位置・順序・平面図紐付けが相互に影響する）であり、逆操作（undo）の定義を誤ると意図しない副作用（例: 削除したマーカーのredoが別のシーンに紐づいてしまう等）を生みやすい。Phase 3のG1・G5・G6で発見されたような「分類時点より実際の到達経路が広い」パターンが、Undo/Redo拡張でも同様に起こり得る（例: ある操作の逆操作が、別の操作のhistory entryと干渉するケース）。
- 対象拡張の範囲（シーン追加・削除・並び替え／マーカー操作／FloorMap画像・配置操作／比較セット名称・構成変更）は範囲が広く、既存の4操作分割と同様、機能単位でさらに細分化する追加の設計整理が実装着手前に必要になる。

## 未確認事項

- 各操作の逆操作（undo）が本当に「元の状態に完全復元」できるか、特にFloorMap画像・配置操作（画像バイナリ自体を含む操作）について、`HistoryManager`が保持するCommand Pattern（クロージャで前後の値を保持する現行方式）がそのまま使えるか、または画像データの扱い方に追加の設計判断が必要かは、本調査では検証していない。
- ユーザー（実際にEditorを使う社内担当者）が実際にどの操作のUndo/Redoを最も必要としているかの実利用ヒアリングは行っていない。
- 案Bの「空間リンク設計」がどの程度のデータモデル変更を要するかは、既存の`docs/vr-runtime-migration.md`等を踏まえた別途の詳細調査が必要であり、本ドキュメントでは規模感の見積もりに留めている。
